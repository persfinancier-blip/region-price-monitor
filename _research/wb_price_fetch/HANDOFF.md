# WB Price Monitor — передача контекста

Документ для того, кто продолжит работу (человек или агент). Состояние на 12.08.2026.

---

## 1. Задача

Собирать с Wildberries **цены и остатки по регионам** и складывать в базу.
Работать должно на сервере, автономно, без человека.

Ключевой факт, ради которого всё затевалось: у WB регион задаётся параметром `dest`
**в самом запросе**, а не сессией. Поэтому один процесс опрашивает сколько угодно городов
подряд — не нужны ни куки, ни браузер, ни прохождение антибота. Это принципиально отличает
WB от Ozon (см. §6).

Разница цен по регионам подтверждена живьём 12.08.2026, товар `629760017`:

| Город | Цена |
|---|---|
| Новосибирск | 2527 ₽ |
| Москва | 2566 ₽ |
| Владивосток | 2591 ₽ |

Разброс 64 ₽, 2.5%.

## 3. Четыре задачи

### 3.1 Прокси

**Статус: сделано в `wb_price.py`, но есть чужая версия, где не сделано.**

На другой машине крутится `wb_parser_pr_qty.py` — производная реализация, в которой прокси
нет. Нужно либо перенести туда механизм, либо перейти на общую кодовую базу.

Что должно быть:

* поля из панели провайдера: host, порт, логин, пароль — либо готовая ссылка одной строкой;
* источники настроек: `proxy.json`, аргументы `--proxy` / `--proxy-host` / `--proxy-user` /
  `--proxy-pass`, флаг `--no-proxy`;
* **автоподбор схемы соединения с прокси.** Это неочевидно и на этом уже спотыкались:
  часть провайдеров слушает plain HTTP, часть ждёт TLS, и по номеру порта не угадать.
  Порт 443 у прокси ≠ https. Пробовать обе схемы, запоминать рабочую на весь прогон;
* проверка выходного IP до начала сбора: адрес, город, оператор. Опрашивать несколько
  сервисов подряд (`api.i.pn`, `ipwho.is`, `ipinfo.io`) — из мобильных пулов первый
  часто недоступен;
* пароль в логах маскировать всегда;
* `proxy.json` держать в `.gitignore`.

Прокси для WB **не обязателен**: регион берётся из `dest`, а не из IP. Нужен, только если
хочется совпадения IP с городом или если домашний адрес упёрся в лимиты.

### 3.2 Батчи

**Статус: сделано в `wb_price.py`. Это причина падения чужой версии.**

Симптом на другой машине: 86459 товаров, 2 города, результат — `498` на Москве и
`статус None` на Новосибирске, ноль собранных строк.

Диагноз: артикулы уходят одним запросом. Параметр `nm` при 86459 позициях превращается
в строку примерно на 900 КБ, такой URL WB не принимает. Разные ошибки при одной причине:
где-то отбил сервер, где-то не пережил транспорт.

Что должно быть:

* `nm` собирается пачками по 50 артикулов (`BATCH_SIZE`), пачки идут последовательно;
* пауза между пачками (сейчас 0.7 с);
* на 429 — backoff `2^attempt + 1`, до трёх попыток;
* сетевой сбой не роняет город: ретрай, потом переход к следующему эндпоинту;
* ошибка по городу не роняет прогон целиком — город помечается и работа продолжается.

Масштаб для планирования: 86459 SKU × 2 города при пачках по 50 — около 3500 запросов
и ориентировочно 150–200 МБ трафика за прогон. Через мобильный прокси это уже заметные
деньги. Стоит фильтровать список активными позициями и не гонять полный прогон часто.

### 3.3 Подключение к таблицам БД

**Статус: код готов, на PostgreSQL не проверен. Доступ к боевой базе под вопросом.**

Реализовано в `wb_db.py`. Драйверы: `psycopg` (3) или `psycopg2`, для локальных проверок —
SQLite. Схема не навязывается: имена колонок определяются автоматически из нескольких
общепринятых вариантов, поэтому подходит к уже существующим таблицам.

Таблица городов — нужны либо координаты, либо готовый `dest`:

| Смысл | Имена колонок |
|---|---|
| код города | `code`, `city_code`, `city`, `region_code` |
| название | `name`, `city_name`, `title` |
| широта / долгота | `lat`/`latitude`, `lon`/`longitude`/`lng` |
| dest | `dest`, `wb_dest`, `dest_id` — если есть, гео-API не дёргается |
| активность | `is_active`, `active`, `enabled` |

Таблица артикулов: `sku`/`nm`/`nm_id`/`article`, опционально `marketplace` (фильтр `wb`)
и `is_active`. Таблица результатов создаётся сама.

Запуск:

```bash
python wb_price.py \
    --db-url postgresql://user:pass@host:5432/parser \
    --cities-table parser_cities \
    --sku-table parser_skus \
    --results-table parser_results \
    --all-cities
```

Подключение можно не писать: берётся из `RPM_DB_URL` либо из
`PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD`.

**Что нужно закрыть:**

1. получить доступ к боевой БД (главная неизвестная — доступа может не быть вовсе);
2. выяснить реальные имена таблиц и колонок, сверить с автоопределением;
3. прогнать на PostgreSQL — проверено пока только на SQLite;
4. решить, дописывать результаты или обновлять, нужен ли уникальный индекс
   по `(collected_at, city, sku)`.

Имена таблиц проверяются регуляркой перед подстановкой в SQL — попытка передать
`no_such; DROP TABLE ...` отбивается. При доработке не потерять эту проверку.

## 4. Что важно знать про API WB

**Два эндпоинта, оба живые:**

1. `https://www.wildberries.ru/__internal/u-card/cards/v4/detail` — внутренний, тот,
   что использует сайт. Требует валидный токен сессии (кука `x_wbaas_token`),
   без него отвечает **HTTP 498**.
2. `https://card.wb.ru/cards/v4/detail` — публичный, работает без токена и отдаёт
   корректные региональные цены.

Логика: пробуем первый, на 498 переключаемся на второй и в этом прогоне больше
к первому не обращаемся. Городить сессию ради внутреннего эндпоинта незачем —
публичный даёт всё нужное.

**HTTP 498 — это не ошибка кода**, а сообщение «нужен токен сессии». Если увидишь его
в логах, ищи не баг, а отсутствие отката.

**dest** берётся у `https://user-geo-data.wildberries.ru/get-geo-info` по координатам,
число лежит в поле `xinfo` строкой `dest=-1257786`. Раньше в проекте это делалось
браузером с человеком — больше не нужно. Результат кэшируется, `dest` меняется редко.

Тонкость: WB считает `dest` по точке на карте, а не по названию города. Сейчас в
`cities.json` центры городов. Для конкретного ПВЗ надо подставить его координаты.

**Цены** приходят в копейках внутри `sizes[].price`:

| Поле | Смысл |
|---|---|
| `basic` | до скидки, зачёркнутая |
| `product` | цена продажи |
| `total` | итог с логистикой, если отдаётся |

Скидки WB-кошелька отдельным полем нет. В коде она оценивается как −2% и помечена
суффиксом `_est`. Не выдавать её за факт.

**Остатки** — `sizes[].stocks[]`, поля `wh` (склад), `qty`, `time1`/`time2` (часы доставки).
Список складов зависит от `dest`: на один товар разные города получают разные склады.
Если во всех городах склад один — это нормально, товар лежит на центральном складе;
проверено на `629760017`, склад `371889`, 42 штуки везде. Тогда региональный сигнал
проявляется в сроках доставки, а не в остатке.

## 6. Чего делать не нужно

**Не браться за Ozon этим же способом.** По нему проведён полный цикл проверок, результат
отрицательный: воспроизведена эталонная конфигурация (Linux + Xvfb + анти-детект браузер
Camoufox + мобильный прокси МТС/Билайн/Tele2, согласованные UA и TLS), Ozon отдаёт капчу
на первом же контакте. Исключены отпечаток браузера, headless-режим, репутация адреса,
рассинхрон IP, TLS-профиль, выбор эндпоинта. Подробности — в
`ИТОГ-проверки-автономного-парсинга.md` в корне проекта.

Отдельно: официальный Seller API Ozon витринную цену **не отдаёт** — параметр
`marketing_price` отключён 12.11.2025, это осознанное решение площадки.

**Не решать капчу автоматически.** Это обход проверки, а не парсинг, и вдобавок означает
войну с антиботом на каждом запросе.

**Не искать цену общим поиском по символу ₽** в ответе или HTML. Так ловятся цены соседних
товаров из блоков рекомендаций. На Ozon это уже приводило к тому, что один артикул за сутки
дал 209, 2805 и 9446 ₽ в разных прогонах.
